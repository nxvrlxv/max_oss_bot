# Собрание собственников в MAX

Чат-бот и мини-приложение для подготовки общего собрания собственников (ОСС): загрузки реестра, сбора позиций жителей, подсчёта голосов с учётом площади и подготовки бумажных бюллетеней. Инициатор видит явку, достижение кворума, результат по вопросу и список собственников, с которыми ещё нужно связаться.

Это MVP помощника организатора. Подтверждение аккаунта MAX не удостоверяет личность человека и его право собственности. В текущей версии соответствие пользователя записи реестра проверяет инициатор вручную.

## Работающая версия

- [Открыть бота в MAX](https://max.ru/t675_hakaton_max_bot).
- [Адрес мини-приложения](https://178-236-254-46.sslip.io/).

Основной сценарий проходится через бота в MAX. Открытие сайта в обычном браузере не даёт авторизацию MAX. Контейнеризация не заменяет работающий продукт: бот, мини-приложение, API и база должны оставаться доступны на протяжении всей проверки. Адреса стенда предоставлены владельцем проекта.

## Основной пользовательский сценарий

1. Инициатор открывает бота и нажимает «Создать собрание». В мини-приложении указывает адрес дома, вопрос, правило подсчёта и срок окончания.
2. Загружает CSV-реестр собственников, проверяет помещения и общую площадь. При необходимости задаёт площадь дома вручную.
3. Публикует собрание и распространяет приглашение ссылкой или QR-кодом. Дополнительно может привязать домовой чат, пригласив в него бота и сделав его администратором, для привязки голосваний и получения приглашений для участия.
4. Житель открывает приглашение в MAX, выбирает помещение и собственника из реестра, затем голосует: «За», «Против» или «Воздержался».
5. Инициатор сверяет заявку и подтверждает её соответствие собственнику. До подтверждения голос сохранён, но не участвует в итогах.
6. На дашборде инициатор отслеживает учтённую площадь и недостающие голоса. Подтверждённый собственник получает PDF-бюллетень в личном диалоге с ботом.
7. После окончания срока голосование недоступно, пользователю показывается итог.

## Состав и архитектура

```text
Клиент MAX + MAX Bridge
        │ HTTPS: мини-приложение и /api/*
        ▼
web — Caddy + собранный React-интерфейс
        ├── /api/* ──► api ──► PostgreSQL (db)
        └── /webhook* ► bot ──► PostgreSQL (db)
                         ↕
                    внешний MAX Bot API

migrate ──► PostgreSQL: миграции до запуска api и bot
```

В режиме `polling` бот сам получает события из MAX; входящий `/webhook` не используется. API также обращается к MAX для проверки токена, уведомлений и отправки PDF.

| Компонент | Назначение |
| --- | --- |
| `webapp/` | React, TypeScript, Vite; экраны инициатора и собственника, MAX Bridge |
| `backend/cmd/api` | Go HTTP API: авторизация, собрания, реестр, заявки, голоса, дашборд |
| `backend/cmd/bot` | Команды, приглашения, привязка чатов, сообщения и доставка файлов через MAX |
| `backend/cmd/migrate` | Применение встроенных SQL-миграций |
| `backend/cmd/seed` | Создание демонстрационного собрания и голосов |
| `backend/cmd/parse-registry` | Отдельная утилита проверки и преобразования CSV |
| `backend/internal/domain` | Подсчёт голосов, пороги и приоритет обхода |
| `backend/internal/storage` | Хранение данных и бизнес-операции в PostgreSQL |
| `backend/internal/docs` | PDF-бюллетени и QR-коды; протокол и отчёт пока являются заготовками |
| `compose.yaml` | Пять сервисов: `db`, `migrate`, `api`, `bot`, `web` |

`db` проходит healthcheck, затем `migrate` применяет миграции. `api` и `bot` запускаются после успешного завершения `migrate`. Для него состояние `Exited (0)` нормально: это одноразовая задача.

## Требования к окружению и зависимости

- Docker Engine или Docker Desktop с Linux-контейнерами и Docker Compose v2 с поддержкой `env_file.required`.
- Свободные порты `80`, `443` и локальный порт PostgreSQL (по умолчанию `5432`).
- Интернет для получения образов, Go- и npm-зависимостей, обращения к MAX и выпуска публичного TLS-сертификата.
- Зарегистрированный бот MAX, действующий токен и настроенное мини-приложение этого же бота.
- Для полного сценария: публичное DNS-имя, указывающее на сервер, доступные извне TCP-порты `80` и `443`, HTTPS-сертификат, которому доверяет клиент MAX. Для проверки двух ролей нужны два аккаунта MAX.

Сборка выполняется внутри Docker: локально устанавливать Go, Node.js или PostgreSQL не требуется. Используемые образы: `golang:1.25-alpine`, `node:22-alpine`, `alpine:3.22`, `postgres:17-alpine`, `caddy:2-alpine`.

Основные библиотеки: Go `pgx/v5`, официальный Go-клиент MAX, `gopdf`, `go-qrcode`; во фронтенде — React, React DOM, TypeScript и Vite. Версии указаны в `backend/go.mod`, `backend/go.sum`, `webapp/package.json` и `webapp/package-lock.json`. Шрифты Liberation Serif для PDF включены в репозиторий вместе с лицензией. В backend-образ добавлен корневой сертификат из `backend/certs/` для соединений с API MAX.

## Настройка и запуск одной командой

Все команды в README предназначены для Bash. Команды Docker выполняются из корня репозитория.

1. Создайте в корне проекта файл `.env` с четырьмя переменными, как на действующем сервере:

   ```dotenv
   DOMAIN=178-236-254-46.sslip.io
   WEBAPP_URL=https://178-236-254-46.sslip.io/
   BOT_TOKEN=
   POSTGRES_PASSWORD=
   ```

2. Заполните пустые `BOT_TOKEN` и `POSTGRES_PASSWORD` действующими значениями. Для другого сервера замените `DOMAIN` и `WEBAPP_URL` на его адреса. Домен должен указывать на сервер запуска Docker. В настройках мини-приложения на платформе MAX укажите тот же HTTPS-адрес: сама переменная `WEBAPP_URL` его там не регистрирует.
3. Остальные переменные задавать не нужно: приложение и Compose используют значения по умолчанию, в том числе `BOT_MODE=polling`. Используйте отдельного бота для локальных экспериментов, чтобы второй получатель событий с тем же токеном не мешал действующему стенду.
4. Запустите **все локальные компоненты одной командой**:

   ```sh
   docker compose up -d --build
   ```

5. Проверьте состояние и логи:

   ```sh
   docker compose ps -a
   docker compose logs --tail=100 migrate api bot web
   ```

6. Проверьте API своего стенда, заменив домен в примере:

   ```sh
   curl https://app.example.ru/api/health
   ```

   Ожидается `{"status":"ok"}`. Этот endpoint подтверждает доступность HTTP API, но не заменяет проверку сценария в MAX.

При `DOMAIN=localhost` Caddy использует локальный сертификат: браузер может ему не доверять. Для технической проверки только на своём компьютере допустима команда `curl -k https://localhost/api/health`. Адрес `localhost` не подходит для открытия приложения с телефона или проверки публичной версии в MAX.

Без действующего токена и доступа к MAX Bot API процессы `api` и `bot` не смогут нормально запуститься: оба проверяют токен при старте. В обычном браузере защищённый API отвечает `401` с просьбой открыть приложение из MAX. В Compose обход авторизации через `DEV_MAX_ID` принудительно отключён.

### Переменные окружения

Для штатного запуска через Docker Compose достаточно четырёх переменных из примера выше. Именно такой набор используется на действующем сервере:

| Переменная | Значение / назначение |
| --- | --- |
| `DOMAIN` | `178-236-254-46.sslip.io` — домен сайта Caddy, без схемы и пути |
| `WEBAPP_URL` | `https://178-236-254-46.sslip.io/` — адрес мини-приложения; тот же адрес задаётся в настройках бота MAX |
| `BOT_TOKEN` | Действующий токен бота; используется процессами `api` и `bot` |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL; Compose использует его при формировании подключения к базе |

Пустые значения секретов в примере нужно заполнить; реальные значения в README не публикуются. `WEBAPP_URL` хранит адрес приложения, но не регистрирует его автоматически в MAX и не используется для построения кнопок бота.

#### Необязательные настройки

Следующие переменные перечислены для справки. Добавлять их в серверный `.env` для обычного запуска не требуется. Расширенный образец находится в `.env.example`.

| Переменная | Значение по умолчанию / пример | Назначение |
| --- | --- | --- |
| `BOT_MODE` | `polling` | Получение событий: `polling` или `webhook` |
| `MAX_API_BASE` | `https://platform-api2.max.ru/` | Базовый адрес MAX Bot API из конфигурации проекта |
| `WEBHOOK_URL` | Пусто | При `webhook` обязательно: `https://ваш-домен/webhook` |
| `WEBHOOK_SECRET` | Пусто | При `webhook` обязательно: случайный секрет для проверки заголовка `X-Max-Bot-Api-Secret` |
| `WEBHOOK_ADDR` | `:8081` | Адрес слушателя бота; Compose принудительно задаёт `:8081` |
| `API_ADDR` | `:8080` | Адрес HTTP API; Compose принудительно задаёт `:8080` |
| `DEV_MAX_ID` | Пусто | Числовой MAX ID для разработки без MAX; в штатном Compose для API принудительно выключен |
| `POSTGRES_USER` | `oss` | Пользователь PostgreSQL |
| `POSTGRES_DB` | `oss` | Имя базы данных |
| `POSTGRES_PORT` | `5432` | Порт базы на хосте, доступный только через `127.0.0.1` |
| `DATABASE_URL` | В Compose формируется автоматически | В Docker задавать не нужно: используется адрес `db:5432` и значения `POSTGRES_*`. При запуске Go-команд вне Docker строку подключения нужно задать отдельно |
| `TEST_DATABASE_URL` | Нет | Только для интеграционных Go-тестов; адрес отдельной тестовой базы |
| `BULLETIN_PDF` | Нет | Необязательный путь сохранения PDF в тесте генерации бюллетеня |

Compose вставляет пароль в `DATABASE_URL` без URL-кодирования. Для этой конфигурации используйте длинный случайный пароль из URI-безопасных символов. Изменение `POSTGRES_*` не перенастраивает уже созданную базу в существующем томе.

Не публикуйте `.env`, токен бота или строку подключения с паролем. После изменения окружения выполните `docker compose up -d`: обычный `restart` не применяет новые значения окружения.

### Порты

| Порт | Доступ | Назначение |
| --- | --- | --- |
| `80/tcp` | Хост → `web` | HTTP, перенаправление на HTTPS и получение сертификата |
| `443/tcp` | Хост → `web` | HTTPS: интерфейс, `/api/*`, `/webhook*` |
| `443/udp` | Хост → `web` | HTTP/3 |
| `127.0.0.1:5432/tcp` | Только локальный хост → `db` | PostgreSQL; порт хоста меняется через `POSTGRES_PORT` |
| `8080/tcp` | Только сеть Compose | HTTP API, проксируется через Caddy |
| `8081/tcp` | Только сеть Compose | Webhook бота, активен при `BOT_MODE=webhook` |

## Внешние сервисы и условия проверки

**MAX — обязательный внешний сервис, который не воспроизводится внутри Docker.** Он предоставляет аккаунты пользователей, подписанные данные запуска (`initData`), события бота, сообщения и доставку PDF. Интерфейс загружает MAX Bridge с `https://st.max.ru/js/max-web-app.js`.

Для проверки нужны рабочий токен, доступ сервера к MAX Bot API, доступ клиента к Bridge и публичному мини-приложению, а также настроенная кнопка открытия приложения у бота. Для PDF пользователь должен начать личный диалог с ботом. Если диалог ещё не открыт, приложение предлагает перейти к боту и нажать «Начать».

Для группового сценария добавьте бота в тестовый домовой чат и предоставьте права администратора с чтением сообщений. Инициатор копирует команду `/bind <номер_собрания>` из раздела «Домовой чат» и отправляет её в группу. После публикации бот отправляет приглашение; для проверки статуса используется `/status`.

При выборе `webhook` задайте `WEBHOOK_URL` и `WEBHOOK_SECRET`; Caddy направляет запросы `/webhook` боту. При старте бот регистрирует текущий адрес и удаляет подписки на другие адреса. При обратном переходе к polling заранее удалите webhook-подписку средствами MAX: код ветки polling этого не делает.

DNS и удостоверяющий центр для публичного TLS также внешние: при корректном домене и сетевой доступности Caddy получает и продлевает сертификат автоматически. Госуслуги, ЕСИА, ЕГРН и другие сервисы подтверждения личности или прав собственности **не интегрированы** и для демонстрации MVP не нужны.

## Работа с данными

В PostgreSQL хранятся профили MAX (`max_id`, имя, username), состояние диалогов с ботом, дома и собрания, реестр помещений и собственников, заявки и голоса. Реестр привязан к конкретному собранию как снимок исходных данных. В него могут входить ФИО, адреса, площади, доли и реквизиты регистрации прав.

CSV загружается в черновик; повторная загрузка заменяет реестр. После публикации вопрос и реестр менять нельзя. При ошибке разбора файл отклоняется целиком. Лимит загрузки — **5 МиБ**, поддерживается UTF-8, в том числе с BOM; разделители — точка с запятой, запятая или табуляция. XLSX напрямую не принимается: его нужно экспортировать в CSV.

Обязательные столбцы:

- `№ помещения`;
- `Адрес объекта`;
- `Правообладатель (правообладатели)`;
- `Долевая площадь, м²`;
- `Общая площадь, м²`.

Одна строка соответствует одному собственнику одного помещения. Поддерживаются строки-продолжения с пустым номером помещения. Формат и необязательные поля описаны в [документации парсера](backend/internal/registry/README.md).

Общая площадь дома по умолчанию считается по уникальным помещениям, а не суммированием повторяющихся строк владельцев. Инициатор может указать большую площадь вручную, если реестр неполный. Площадь меньше суммы помещений не принимается.

Вес подтверждённого голоса — долевая площадь собственника. Повторное голосование обновляет выбор, не создавая дополнительного веса. Пока заявка не подтверждена, выбор хранится в заявке и в явку не включается. В текущей реализации кворум требует **более 50%** общей площади; доступны правила решения: более половины участвующей площади, не менее 2/3 всей площади или вся площадь. Это описание алгоритма MVP.

Доступ к управлению собранием проверяется по MAX ID инициатора. Подпись `initData` проверяется на сервере; срок действия — 24 часа. Посторонний пользователь должен получить приглашение, чтобы открыть собрание. Ссылка и QR содержат токен доступа, поэтому их следует распространять среди участников. Выбор собственника показывает данные реестра участнику приглашённого собрания; для демонстрации используйте вымышленные данные.

Постоянные данные PostgreSQL находятся в томе `pgdata`; данные и сертификаты Caddy — в `caddy_data` и `caddy_config` (Compose добавляет префикс проекта). Остановка и пересоздание контейнеров без удаления томов сохраняют данные. Автоматическое резервное копирование и политика удаления персональных данных в MVP не настроены. Сформированные PDF передаются во внешний MAX и могут остаться у получателя после удаления собрания.

## Тестовые данные

Для ручной проверки используйте [backend/testdata/demo_house.csv](backend/testdata/demo_house.csv): демонстрационный дом в г. Примерске, вымышленные собственники и доли. Загружайте его через экран черновика. Не используйте реальные реестры при публичной демонстрации.

Для быстрого наполнения дашборда после запуска Compose можно создать отдельное демо-собрание утилитой `seed`:

1. Отправьте боту текстовую команду `/start` и найдите свой числовой MAX ID в `docker compose logs --tail=100 bot`.
2. Подставьте этот ID вместо `123456789`:

   ```sh
   docker compose run --rm migrate seed -initiator 123456789 -rule soft -turnout 0.4 -pending 0.1
   ```

3. Откройте «Мои собрания» у бота. Seed создаёт новое опубликованное собрание на 14 дней с реестром из `/app/testdata/demo_house.csv`; примерно 40% записей собственников получают голоса, примерно 10% созданных голосов остаются без подтверждения. Фактические числа выводятся в лог.

Демо-пользователи имеют отрицательные `max_id`. Их голоса создаются через операции заявки, голосования и подтверждения, но настоящих аккаунтов MAX и личных диалогов у них нет. Каждый запуск создаёт **новое** собрание, а не обновляет прежнее; распределение зависит от ID собрания.

Для проверки реальными аккаунтами создайте отдельное собрание через интерфейс либо используйте seed с `-turnout 0`: подтверждённые демо-записи иначе уже займут соответствующих собственников. Для черновика добавьте `-publish=false`.

Тестовое незавершённое собрание можно удалить через интерфейс инициатора. Завершённые собрания защищены от удаления. Полный сброс тестовой базы удалением томов описан ниже и допустим только на отдельном тестовом стенде.

## Пошаговая проверка и ожидаемое поведение

1. **Запуск.** Выполните команду запуска, проверьте `ps -a`, логи и `/api/health`. Ожидается успешная миграция и работающие `db`, `api`, `bot`, `web`.
2. **Вход инициатора.** Первым аккаунтом откройте бота, нажмите «Начать», затем «Создать собрание». Должна открыться форма внутри MAX.
3. **Черновик.** Укажите тестовый адрес, вопрос, правило «Большинство от проголосовавших» и будущий срок. Загрузите `backend/testdata/demo_house.csv`. Должны появиться сведения о реестре и площадь дома. Без реестра публикация недоступна.
4. **Публикация.** Нажмите «Опубликовать». Должны появиться дашборд, ссылка и QR-приглашение. Для групповой проверки привяжите чат командой из раздела «Домовой чат» и проверьте объявление и `/status`.
5. **Голос до подтверждения.** Вторым аккаунтом откройте приглашение, выберите квартиру № 2 и Степанова Олега Николаевича, проголосуйте «За». Заявка должна появиться у инициатора, а голос — сохраниться с ожиданием подтверждения. Учтённая явка пока не увеличивается.
6. **Подтверждение.** В разделе «Заявки» инициатор подтверждает соответствующую запись. На свежем собрании без других голосов учтённая площадь «За» и явка должны стать **61 м²** — площадью собственника квартиры № 2. Дашборд обновляется периодически (примерно раз в 10 секунд).
7. **Изменение голоса.** Тем же жителем измените выбор на «Против». Ожидается перенос 61 м² из «За» в «Против» при неизменной общей явке; повторного учёта нет.
8. **Документы.** Житель запрашивает бюллетень для подписи и получает PDF в личном диалоге с ботом. Если появляется предложение начать диалог, перейдите по нему и нажмите «Начать». Инициатор нажимает «Бланки для обхода» и получает PDF для собственников, чьи голоса ещё не учтены.
9. **Отрицательные проверки.** Откройте `/api/me` обычным браузером без MAX — ожидается `401`. Попробуйте загрузить CSV без обязательной колонки в отдельный черновик — ожидается ошибка без частичного импорта. Попытка подтвердить одного собственника за двумя разными аккаунтами должна быть отклонена.
10. **Окончание срока.** Для отдельного короткого теста задайте ближайший будущий срок (форма использует московское время). После его наступления обновите экран: новые голоса не принимаются, отображается итог. Кнопки ручного завершения в текущем интерфейсе нет; серверный endpoint `POST /api/meetings/{id}/finish` реализован.
11. **Сохранность.** Перезапустите сервисы по инструкции ниже и заново откройте собрание из MAX. Реестр, заявки и голоса должны сохраниться.

Примеры расчёта для условного дома площадью 100 м²:

| Учтённые голоса | Правило | Ожидаемый результат |
| --- | --- | --- |
| 50 м² «За», остальные не участвовали | Большинство участвующих | Кворума нет: ровно 50% недостаточно |
| 60 м² «За», остальные не участвовали | Большинство участвующих | Кворум есть, решение принято |
| 60 м² «За», остальные не участвовали | 2/3 всей площади | Кворум есть, порог решения не достигнут |
| 60 м² «За» до подтверждения заявки | Любое | Учтённая явка 0 м² |

### Автоматические проверки

При установленном Go 1.25 или новее из каталога `backend`:

```sh
go test ./...
```

Без `TEST_DATABASE_URL` интеграционные тесты API и хранилища пропускаются. **Не направляйте их в рабочую базу: тесты пересоздают схемы `public` и `api_test`.** Создайте отдельную пустую базу с правами изменения схем, затем задайте её URL. Пример для Bash с предварительно созданной базой `oss_test`:

```bash
export TEST_DATABASE_URL='postgres://oss:YOUR_PASSWORD@localhost:5432/oss_test?sslmode=disable'
go test ./...
unset TEST_DATABASE_URL
```

Для проверки сборки фронтенда при установленном Node.js 22+ выполните из `webapp`:

```sh
npm ci
npm run build
```

Автотесты проверяют внутреннюю логику, но не подтверждают доступность реального бота, доставку сообщений или работу клиента MAX. Их нужно дополнить сценарием выше.

## Известные ограничения

- **Нет доверенной идентификации личности и проверки права собственности.** MAX ID и подписанные данные запуска подтверждают аккаунт MAX, но не то, что им пользуется конкретный собственник. Совпадение имени с реестром также не является доказательством. Сейчас инициатор подтверждает заявки вручную; для надёжной идентификации нужна отдельная интеграция с Госуслугами/ЕСИА или другим доверенным сервисом, а для прав собственности — проверяемый источник соответствующих данных. В MVP этих интеграций нет.
- Электронная подпись, проверка подписанных бумажных бюллетеней и их автоматический импорт не реализованы. PDF — подготовленный бланк для дальнейшей работы организатора; нажатие кнопки в приложении не создаёт подписанный документ.
- Генерация итогового протокола и отчёта не реализована: `backend/internal/docs/protocol.go` и `report.go` содержат только заготовки. Текст приветствия бота упоминает протокол, но получить его в текущей версии нельзя.
- Одно собрание содержит один вопрос. Выбор правила подсчёта и качество исходного реестра остаются ответственностью инициатора; система не подбирает правило автоматически по содержанию вопроса.
- Проверка полноты и актуальности реестра по внешнему источнику отсутствует. CSV-парсер не гарантирует полноту суммы долей; при неполном реестре нужно отдельно проверить площадь дома.
- Один аккаунт не может представлять разных подтверждённых людей в рамках собрания; ограничение опирается на сопоставление ФИО. Заявки одного человека на несколько помещений поддерживаются. Одновременно допускается не более пяти заявок без ответа.
- Полностью автономного режима без MAX нет. Сбои внешнего API, ограничения доступа к боту или недоступность публичного HTTPS-адреса мешают основному сценарию.
- Резервное копирование и отказоустойчивое развёртывание не входят в текущую конфигурацию.

## Остановка, повторный запуск и сброс

Остановить сервисы, сохранив контейнеры и данные:

```sh
docker compose stop
```

Запустить их снова:

```sh
docker compose start
```

Перезапустить работающие процессы без изменения конфигурации:

```sh
docker compose restart
```

После изменения кода или Dockerfile пересобрать и запустить:

```sh
docker compose up -d --build
```

Удалить контейнеры и сеть, сохранив базу и сертификаты в томах:

```sh
docker compose down
```

После этого повторный запуск — `docker compose up -d --build`. Используйте ту же директорию и имя Compose-проекта, чтобы подключились прежние тома.

**Только для полного сброса отдельного тестового стенда:** следующая команда безвозвратно удаляет тома с базой данных и сертификатами Caddy. Она не подходит для остановки работающей демонстрационной версии.

```sh
docker compose down --volumes
docker compose up -d --build
```

После сброса миграции применятся к пустой базе; тестовый CSV нужно загрузить заново или повторить seed. Срок доступности действующего бота и мини-приложения должен покрывать весь период проверки решения.
