# План MVP — помощник подготовки ОСС в MAX

Технический план: что входит в MVP, в каком порядке разрабатывается, как устроен проект.
Продуктовая часть (проблема, гипотеза, сценарии, масштабирование) — в `concept.md`.

---

## 1. Принятые решения

Ключевые развилки, пройденные при проектировании, и итоговый выбор.

| Вопрос | Решение | Обоснование |
|---|---|---|
| Ключ дома | `chat_id` домового чата | Уникален и стабилен, в отличие от строки адреса. Ложных совпадений нет по определению |
| Переиспользование реестра между собраниями | Нет, реестр грузится заново на каждое собрание | Без собственного реестра синхронизация изменений превращается в имитацию интеграции |
| Хранение реестра | Снимок на дату, привязан к собранию, удаляется через N дней после завершения | Состав собственников определяется на дату собрания. Снимок = приложение к протоколу |
| Варианты ответа | Всегда три: за / против / воздержался | Свободные варианты не конвертируются в бюллетень и протокол |
| Голос до подтверждения | Сохраняется со статусом `pending`, в подсчёт не идёт | Экран «ожидайте подтверждения» — тупик, из которого не возвращаются |
| Куда уходят бланки | Персональный бланк — собственнику в личку, комплект по неохваченным помещениям — инициатору | Бланк содержит ФИО, долю и реквизиты права. В общий чат отправлять нельзя |
| Транспорт бота | Вебхук на проде, `BOT_MODE` для локального запуска | Токен один, одновременно активен только один канал уведомлений |
| Собственный публичный API | Не заявляется | Баллов не даёт, но тянет openapi.yaml, DATA-API.yaml и дополнительные обязательные проверки |

## 2. Must Have

Критерий отбора: без функции сквозной сценарий не проходится от начала до результата.

### Инициатор

| № | Функция | Что входит | Где |
|---|---|---|---|
| 1 | Вход и создание собрания | `/start`, сохранение `max_user_id`, `/init_sobr`, кнопка в мини-приложение | бот |
| 2 | Привязка чата | `bot_added` → кнопка → проверка прав → запись `chat_id` | бот |
| 3 | Данные дома | Адрес, число подъездов, общая площадь помещений | мини-апп |
| 4 | Импорт реестра | Парсинг CSV/XLSX, нормализация доли и площади, отчёт валидации | мини-апп |
| 5 | Вопрос и срок | Формулировка, правило порога, даты начала и окончания | мини-апп |
| 6 | Публикация | Уведомление в чат: текст, ссылка с `meeting_id`, QR | бот |
| 7 | Подсчёт и разрыв | Взвешенная сумма, сверка с порогом, недостающие метры, список помещений для обхода | ядро + мини-апп |
| 8 | Подтверждение привязок | Очередь заявок, подтверждение и отклонение | мини-апп |
| 9 | Документы | Бланки по неохваченным помещениям, справка, черновик протокола | воркер + бот |

### Собственник

Вход по ссылке → выбор помещения → голосование → персональный бланк после подтверждения.
Отдельных функций не добавляет: целиком укладывается в пункты 4, 7, 8, 9.

### Won't Have (называется явно)

ЕСИА и Госуслуги, автозагрузка квартир, интеграция с ГИС ЖКХ, передача протокола во внешнюю систему, ЭЦП бюллетеней, переиспользование реестра между собраниями, история собраний, счётчики, оплата ЖКУ, заявки в УК, страховка, умный дом, чат внутри продукта, мультидом.

## 3. Этапы разработки

Порядок определяется блокировками, а не важностью функций.

### Этап 0 — параллельный трек, с первого дня

Токен, домен, HTTPS-сертификат, «hello world» мини-приложения, открывающийся **и в мобильной, и в веб-версии MAX**. Один человек.

Если всплывёт на десятый день — проект не сдан.

### Этап 1 — доменное ядро (полдня)

Чистые функции без БД и фреймворка:

- вес голоса из доли и площади;
- суммы по вариантам;
- сверка с порогом **со строгим неравенством** (закон говорит «более чем», ровно 50% кворума не даёт);
- разрыв в метрах;
- жадный подбор минимального набора помещений для обхода.

Покрывается тестами сразу. Первым, потому что здесь вся ценность продукта, и после этого главный риск снят.

### Этап 2 — импорт реестра (день)

Парсер CSV/XLSX, нормализация двух форматов (доля дробью или процентом / площадь в м²), проверка суммы долей, сверка суммы площадей с общей площадью дома, отчёт для пользователя.

Вторым, потому что блокирует всё: без площадей нет ни порога, ни голосов, ни бланков.

**Контракт API фиксируется в конце этого этапа** — до того, как кто-либо начнёт писать экраны.

### Этап 3 — тонкий сквозной срез (два дня)

Не «сначала бэкенд, потом фронт», а один путь целиком на заглушках: бот отдаёт ссылку → мини-приложение открывается → валидация `initData` → голос сохраняется → число на дашборде меняется. С одним вопросом, без подтверждений и документов.

Третьим, потому что интеграция бот ↔ мини-приложение ↔ API — самый недооценённый риск, а критерий её корректности весит 12%.

### Этап 4 — обрастание среза (три-четыре дня)

Подтверждение привязок, очередь заявок, экран разрыва с маршрутом обхода, публикация статуса в чат, состояния загрузки и ошибок на каждом экране.

### Этап 5 — документы (параллельно, любым свободным человеком)

Генерация бланков, справки, черновика протокола. Не блокирует ничего, но легко съедает два дня на кириллические шрифты и вёрстку — начинать заранее.

### Этап 6 — сдача (два дня)

Docker, README по списку из брифа, `.env.example`, прогон на утечку секретов, демо на seed-данных, репетиция.

**Заморозка функциональности за четыре дня до дедлайна.** Фича, добавленная позже, статистически чаще ломает основной сценарий, чем добавляет к оценке.

## 4. Дальнейшие шаги

| Горизонт | Что добавляется | Что требуется извне |
|---|---|---|
| К финалу | Напоминания незавершившим, оргвопросы (председатель, секретарь, счётная комиссия), несколько вопросов в повестке, материалы собрания | — |
| Пилот с УК | Кабинет управляющей организации, реестр из учётной системы, портфель домов | Договорённость с УК |
| Подтверждённая личность | ЕСИА вместо ручного подтверждения | Доступ к ЕСИА, статус информационной системы |
| Юридически значимое ОСС | ЕГРН, ГИС ЖКХ, передача протокола | Интеграция с государственными системами, статус оператора |

Ядро при этом не меняется — меняется источник доверия.

## 5. Архитектура

```
MAX client ──▶ bot (webhook)  ──┐
           └─▶ mini-app (HTTPS) ├──▶ api ──▶ PostgreSQL
                                 └──▶ worker (документы, рассылки)
```

Четыре процесса, один репозиторий, один язык на бэкенде, один Docker-образ с разными командами запуска.

Бот и воркер ходят в БД напрямую через общий слой `storage`, а не по HTTP в собственный API: лишний сетевой вызов между своими же процессами на MVP добавляет точку отказа и ничего не даёт. При росте нагрузки бот выносится за API — на одном доме это преждевременная сложность.

### Почему именно так

**`internal/domain` без зависимостей.** Подсчёт голосов — единственное место, где ошибка не видна глазом: неправильный результат выглядит как правильный. Изоляция от БД и HTTP позволяет покрыть его тестами за полчаса и защищать на вопросах жюри.

**`registry` отдельно от `storage`.** Импорт — преобразование внешнего мира во внутреннюю модель, он будет меняться под каждый новый формат выгрузки УК.

**`cmd/` из четырёх точек входа при одном образе.** Время сборки укладывается в лимит 5 минут, дублирования кода нет.

**`templates/fonts` в репозитории.** Базовые шрифты PDF-библиотек кириллицу не содержат — обнаруживается за час до сдачи пустыми прямоугольниками вместо текста.

**`testdata/demo_house.csv` под версионным контролем.** Демо-дом — часть продукта: на нём проходит и демонстрация, и проверка жюри по README.

## 6. Схема данных

```sql
meetings     (id, chat_id, initiator_user_id, address, entrances_count,
              total_area, question, rule_json, notice_sent_at,
              starts_at, ends_at, status)

units        (id, meeting_id, number, type, entrance, floor, area)

owners       (id, unit_id, kind, full_name, org_name, ogrn,
              share, ownership_doc, max_user_id, status)

votes        (id, meeting_id, owner_id, choice, weight_area, status,
              UNIQUE (meeting_id, owner_id))

bot_dialogs  (max_user_id PK, started_at, is_active)
```

### Инварианты

- **`rule_json` хранит правило порога как данные**, а не как `if` в коде. Одно ядро обслуживает большинство, 2/3 и 100%. Структура: `{base, threshold, op, scope}` — `scope` нужен для нетиповых случаев вроде кворума по подъезду.
- **`weight_area` фиксируется в самом голосе.** Правка реестра не меняет задним числом уже подсчитанный результат.
- **`total_area` вводится вручную**, а не считается суммой из файла. Иначе неполный реестр молча даст заниженный порог, и сверять будет нечем.
- **Уникальность по `(meeting_id, owner_id)`**, переголосование через upsert до дедлайна.
- **Всё каскадно удаляется вместе с собранием** — это позволяет реализовать автоудаление снимка одной строкой.

## 7. Обработка апдейтов

Бот один, токен один, поток обновлений один. Разделение — по типу чата (`dialog` / `chat`) и типу события.

| Событие | Тип чата | Действие |
|---|---|---|
| `bot_started` | dialog | Запись в `bot_dialogs`, разбор deep-link payload, кнопка «Открыть голосование» |
| `bot_added` | chat | Предложение привязать чат к собранию |
| `message_callback` | chat / dialog | Разбор payload: привязка, выдача ссылки, отказ от напоминаний |
| `message_created` | dialog / chat | Только команды: `/start`, `/init_sobr`, `/status` |
| `bot_removed`, остановка диалога | chat / dialog | Деактивация привязки или диалога |

Правила эндпоинта вебхука:

1. **Отвечать 200 сразу**, работу класть в очередь. Иначе обновления копятся и ретраятся.
2. **Считать доставку ненадёжной**: одно обновление может прийти дважды, все обработчики идемпотентны.
3. **Проверять, что запрос от MAX**: секретный сегмент в пути из `.env`, подпись — если платформа её поддерживает.
4. **Неизвестные типы событий игнорировать молча** — API в бете, набор типов уже менялся.

Рассылки инициируются планировщиком, а не апдейтами: отдельный воркер с троттлингом под лимит 30 rps.

Подписка на вебхук перерегистрируется при старте сервиса, если адрес изменился. Иначе после передеплоя бот молча перестаёт получать события.
